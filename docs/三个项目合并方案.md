# 三个开源项目能不能合成一个？

结论先说：**能，但不是「把三个仓库合并」——是「新建一个宿主程序，把三者的能力各取一块」**。
技术上没有硬障碍，真正的约束来自 **平台（Android vs 桌面）** 和 **许可证（非商业 / LGPL / 专有 SDK）**。

---

## 一、三个项目分别是什么

| 项目 | 技术栈 | 平台 | 许可证 | 核心能力 |
| --- | --- | --- | --- | --- |
| **Biu**（wood3n/biu） | Electron + React 19 + TypeScript + rsbuild + zustand + electron-store | Windows / macOS / Linux | **PolyForm Noncommercial 1.0.0**（禁止商业使用） | B 站音乐搜索、播放、歌单、收藏、下载、歌词、扫码登录、迷你播放器、托盘、全局快捷键 |
| **DesktopFriends**（Tosuke-sama/DesktopFriends） | Tauri（Rust）桌面端 + Capacitor（Android）+ Vue 3 + Live2D Cubism + LLM Agent | Windows / macOS / Android | `package.json` 写 MIT，但**仓库里没有 LICENSE 文件**（实测 `/LICENSE` 404） | Live2D 桌面伙伴、AI 对话/记忆/工具调用、桌面小组件、P2P 联机 |
| **ANeko**（pass-with-high-score/ANeko） | Kotlin + Jetpack Compose + Hilt + Room | **仅 Android** | **LGPL-2.1** | 屏幕悬浮的像素猫：跟着手指跑、沿屏幕边缘走、皮肤系统（XML + PNG 序列帧）、多语言 |

三个项目其实处在三个不同的「层」：

- Biu = **内容/播放层**（音源 + 播放器）
- DesktopFriends = **伙伴表现层**（Live2D + 人格）
- ANeko = **桌面行为层**（一个会自己散步的小生物）

它们并不冲突，反而正好互补——这正是「能合」的根本原因。

---

## 二、为什么不能直接合并仓库

1. **运行时不同**：Electron（Chromium + Node）、Tauri（Rust + WebView2）、Android 原生（Kotlin）。
   三套壳没法塞进同一个进程。
2. **平台不同**：ANeko 是 Android 悬浮窗（`SYSTEM_ALERT_WINDOW`），它的「桌面」是手机桌面；
   在 Windows 上对应的能力是「透明置顶无边框窗口 + 鼠标穿透」，只能重写行为，不能搬代码。
3. **许可证不同**：
   - Biu 是 **非商业**许可，合并后整体就不能商用；
   - ANeko 是 **LGPL-2.1**，静态/打包进 Electron 时要注意「可替换、可重链接」的义务；
   - DesktopFriends 声明的 MIT 没有 LICENSE 文件，严格来说授权状态不完整；
     它内置的 **Live2D Cubism Core 是专有 SDK**，Hiyori 示例模型也有单独的使用条款，不能随意随包分发。
4. **依赖体量**：Biu 是完整产品（几百个源文件），DesktopFriends 是 pnpm monorepo（桌面/移动/服务端/多个包），
   直接 merge 会得到一个几乎无法维护的仓库。

## 三、可行的合并方式：一个宿主 + 三个适配层

```
┌──────────────────────────────────────────────────────┐
│                    宿主（Electron）                    │
│  main: 窗口/托盘/快捷键/开机自启/单实例/持久化          │
├──────────────────────────────────────────────────────┤
│  表现层  Pet Layer                                     │
│   ├─ SpritePet（Canvas 序列帧 / 矢量，ANeko 行为移植）  │
│   └─ Live2DPet（pixi-live2d-display 或 Cubism SDK）    │
│        ↑ 统一接口：setState(idle|walk|dance|sleep)     │
├──────────────────────────────────────────────────────┤
│  播放层  Player Layer                                  │
│   ├─ BiliSource：WBI 签名 / 搜索 / playurl / 音轨       │
│   └─ 播放内核：<audio> 或 WebAudio，队列/模式/收藏       │
├──────────────────────────────────────────────────────┤
│  联动层  Sync                                          │
│   播放状态 → 宠物动作；宠物点击 → 播放器；托盘/媒体键    │
└──────────────────────────────────────────────────────┘
```

三种落地路线，按工作量排序：

### 路线 A：以 Biu 为底座，加一个宠物窗口（最省力，推荐）

保留 Biu 全部功能（登录、歌单、下载、歌词、迷你播放器），只新增：

- 一个透明置顶的宠物 `BrowserWindow`（约 200 行主进程代码 + 一个 Canvas/Live2D 页面）；
- 一个 `playback` 状态桥（Biu 的 zustand store → IPC → 宠物）；
- 托盘里加「显示小鲸鱼」。

工作量：**3～5 天**。代价：整体继承 Biu 的**非商业**许可；Live2D 模型需自备并遵守 Cubism 许可。

### 路线 B：全新宿主，重写播放器 + 宠物（本仓库采用的方案）

- 播放器只保留「搜索 / 播放 / 队列 / 收藏」，用原生 HTML/CSS/JS，没有 React 负担；
- 宠物用 Canvas 矢量绘制，零素材依赖，行为参考 ANeko；
- B 站接口自行实现 WBI 客户端（不复制 Biu 代码，规避许可纠缠）。

工作量：**1～2 周**能到「日常可用」；优点是可商用（只要不抄 Biu 的代码和素材）、包体小、可控。

### 路线 C：三端联动（最接近「真正合体」）

- 桌面端（路线 A/B）+ Android 端保留 ANeko 作为「第二屏宠物」；
- 两端通过局域网 WebSocket 同步播放状态，手机上的猫跟着电脑里的歌跳舞；
- 还可以接入 DesktopFriends 的 LLM Agent，让猫能聊天、点歌。

工作量：**1～2 个月**。适合当作品集/毕设，不适合当第一版。

## 四、许可证对照（决定你能不能发布）

| 组合方式 | 结果 | 能否商用 | 注意 |
| --- | --- | --- | --- |
| 直接 fork Biu 改 | 衍生作品 | ❌ 需授权 | PolyForm NC 只允许非商业用途 |
| 移植 ANeko 行为代码 | 衍生作品 | ✅（LGPL） | 需开源相应部分、保留版权声明、允许替换 |
| 内嵌 Live2D Cubism Core | 使用专有 SDK | 视 Live2D 许可 | 有营收门槛，需申请发行许可 |
| 只借鉴思路、自己实现（本仓库） | 独立作品 | ✅ | 不复制 Biu 的代码/素材；桌宠素材来自 MIT 的 dsh-whale-widget，已保留许可与署名 |

> 一句话：**自己写播放器 + 用 MIT 素材做桌宠 + 用户自备 Live2D 模型**，是许可上最干净的做法。

## 五、这个 Demo 验证了什么

`BiliWhaleMusic/` 就是路线 B 的最小可用版本，跑通了整条链路：

1. **B 站匿名可用**：`buvid3` → WBI 签名 → 搜索（20 条真实结果）→ 视频详情 → DASH 音频流（最高 192K）→ 播放。
2. **多 P 展开**：点开「100 首热门合集」，自动变成 100 个可播放条目（截图里正在播 P1）。
3. **状态联动**：播放时桌宠切到 `dance` 状态；暂停/切歌实时同步；气泡显示曲名。
4. **桌宠行为**：固定在右下角、不自己走动；按住拖动、松手记住位置；单击摸摸、双击开播放器、右键菜单。
5. **系统集成**：托盘菜单、媒体键全局快捷键、隐藏到托盘、设置（大小/置顶/音量/Cookie）。

截图见 `shots/`：`player.png`（播放中）、`pet-idle.png`、`pet-dance.png`。

## 六、追加：桌宠换成 dsh-whale-widget

桌宠最早是自绘小猫，后来删掉，只保留 **dsh-whale-widget** 的小鲸鱼——它是 DSH Web 界面
右下角的常驻挂件（DeepSeek 余额 + 气泡系统），`v0.4.2`，MIT，作者 MeteorNOX。
放到桌面上之后，**不再自己走动**，只保留「固定站位 + 拖动 + 位置记忆」，更接近挂件的使用习惯。

它为什么适合当桌宠：

- `assets/DSniang1.png` 是带透明通道的 Q 版小鲸鱼娘（610×610），本身就是「挂件」画风；
- `assets/DSniang02.png` 直接把**思考气泡**画进了图里（白底 + 深蓝描边 + 三点尾巴），
  这是它的视觉签名，照着复刻气泡即可；
- `assets/rua.gif` 是摸摸动图，点击反馈直接有了；
- 角色可换（`whale-roles/`），意味着以后可以做成「皮肤包」。

在 Electron 里的落地方式：

| widget 里的东西 | BiliWhaleMusic 里的实现 |
| --- | --- |
| 角色 PNG | `assets/whale/whale.png`，CSS keyframes 做漂浮/蹦跳/跳舞/打盹 |
| 白底深蓝气泡 | 纯 CSS 复刻（`.bubble-body` + `.bubble-dots`），文字色 `#22305f` |
| 点击轮播气泡序列 | 单击改为弹出播放控制条；双击摸头（rua + 爱心 + 气泡） |
| rua.gif 摸摸 | 双击时浮出 1.1s |
| 拖拽 + 吸附 | 沿用原来的「指针捕获 + 主进程跟随光标」，松手夹回屏幕并记住位置 |
| 余额数据 | 暂未接（需要 DeepSeek key）；接口位置已想好：气泡模块化 + 定时刷新 |

许可证：MIT，已把 `LICENSE` 随素材放进 `assets/whale/`，README 里也做了署名。

## 七、B 站登录与收藏（后加）

看自己的收藏，绕不开登录。做法是**直接用 B 站官方登录页**，而不是自己拼扫码协议：

- 登录入口放在标题栏的账号胶囊里（全局可见），不再把 Cookie 输入框塞进设置；登录后显示头像昵称，
  点开是「打开 B站收藏 / 退出登录」。
- 开一个 660×840、可自由缩放的子窗口加载 `https://passport.bilibili.com/login`，扫码 / 密码 / 短信
  三种方式都是 B 站自己的页面，不用维护登录协议；页面按桌面宽度设计，窗口尺寸变化时按
  `scrollWidth/clientWidth` 自动调 `zoomFactor`（窄了缩小、拉宽后恢复），保证二维码不被裁掉。
- 主进程每 700ms 读一次 `session.cookies`，出现 `SESSDATA` 就调 `nav` 验证，成功后把
  `SESSDATA / bili_jct / DedeUserID / buvid3 / buvid4` 拼成 Cookie 串存本地，并记下 `mid`。
- 收藏夹用 `/x/v3/fav/folder/created/list-all`（列收藏夹）和 `/x/v3/fav/resource/list`（列内容），
  匿名访问只会返回空，必须带 Cookie。
- 页面里「B站收藏」标签：未登录显示登录卡片；登录后显示头像/昵称/UID、收藏夹切换、
  视频列表与「加载更多」，点条目直接进播放队列。
- 退出登录同时清本地 Cookie 和 Electron 会话 Cookie。

## 八、如果继续做，优先补什么

1. **收藏夹写入**：目前只读；可以加「收藏到 B 站」按钮，走 `fav/resource/deal`（需 csrf=bili_jct）。
2. **把 widget 的余额能力接进来**：读 DSH 凭证里的 `DEEPSEEK_API_KEY` 或账号登录态，
   气泡里显示余额/今日消耗，才算真正「镜像」了 widget（约 1 天）。
3. **角色包**：支持把 `whale-roles/*.png` 拖进设置，热切换形象（约 1 天）。
4. **歌词**：B 站字幕接口或 lrclib，桌面歌词窗（约 2 天）。
5. **打包**：electron-builder，做便携版 + 安装包（约半天）。

这些能力 Biu 都已经实现过，可以直接对照它的接口层（`src/service/*`）补齐——但记得遵守它的非商业许可。
